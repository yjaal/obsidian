## 现代 Agent = LLM + 上下文 + 工具

- LLM 是 Agent 的大脑：它不只是一组模型参数，而是 Agent 的整个决策内核——理解意图、思考规划、做出判断。就像人类大脑不只是神经元的集合，还包括通过经验塑造的思维方式，LLM 的能力也来自两部分：预训练所积累的世界知识与语言能力，以及后训练所固化的决策策略——后者的具体技术（如监督微调与强化学习）将在第八章展开。
- 上下文是 Agent 的眼睛：它不只是输入给模型的那段文本，而是 Agent 在每个决策点收到并保留的信息表示——来自环境的观察、用户记忆、领域知识、自身状态和任务进展。
- 工具是 Agent 的手脚：这里的“工具”指 Agent 用来感知或改变外部世界的接口，包括工具定义、调用协议和适配器——从预定义的工具调用到动态生成代码，从委托子 Agent 协作到主动与用户沟通。

换一种更直观的说法：Agent = 大脑 + 眼睛 + 手脚。大脑负责思考和决策，眼睛接收环境提供的观察，手脚将决策转化为作用于环境的行动。


### 观察空间与动作空间：模型与世界的接口

观察通道与动作接口共同构成了 Agent 与外部环境之间的边界。 Harness 把环境返回的观察转换为模型能够处理的上下文，再把模型选择的行动转换为对环境的工具调用。没有通过观察通道进入上下文的信息，对模型来说就像不存在；没有被动作接口允许的操作，模型即使知道该怎么做，也只能停留在文字建议上。

因此，在底层模型固定时，提升 Agent 任务表现最主要的系统工程手段，往往就是重新定义或扩展观察空间与动作空间。用本书的术语说，就是扩展上下文和工具。许多看似需要“更聪明模型”的问题，其实只是接口问题：把任务所需的数据纳入上下文，或把完成任务所需的操作封装成工具，原本不可解的任务就可能变得可解。

### 工具：Agent 的手脚

感知工具让 Agent 能访问信息：搜索引擎提供实时网络数据，文件系统读取本地文档，API 和数据库则对接外部服务和企业核心数据。

执行工具让 Agent 改变世界：代码执行、文件操作、系统命令、外部 API 调用——决策由此变成实际行动。

协作工具让 Agent 与其他 Agent 分工合作：委托子 Agent 完成专项任务，在关键决策点请求人类确认，或在多 Agent 系统中协调行动。

事件触发工具与前三类在调用方式上有本质的区别——它们不是 Agent 主动调用的，而是作为外部输入来驱动 Agent 开始执行任务。比如收到一封新邮件、到了某个预定时间点、或另一个系统发出了 Webhook 回调，这些事件会激活 Agent，让它开始后续的思考和行动。事件适配器同样是 Environment 向 Agent 提供观察的通道，因此本书把它归入广义的工具体系。

用户沟通工具是 Agent 主动与用户建立连接、传递信息的渠道。与执行工具改变外部世界不同，用户沟通工具专注于信息的传递和交互——通过文字消息、语音通话、邮件等方式，将 Agent 的执行进展或主动关怀传达给用户。

工具设计的核心原则是：
**通用基础能力用于组合与探索；专用工具用于约束高风险和强业务规则操作**。



### 上下文： Agent 的眼睛

系统提示词（System Prompt）：与用户每次输入的提示词不同，系统提示词由开发者编写，在整个对话过程中保持不变，相当于 Agent 的“岗位说明书”——定义它的身份、权限和行为准则。通过提示工程（Prompt Engineering）精心设计系统提示词，我们可以塑造 Agent 的工作方式。系统提示词中还会包含跨会话保存的用户记忆（用户偏好、历史行为、背景设定等个性化信息，详见第三章）和动态注入的环境状态。

工具定义 （Tool Definitions）：声明 Agent 可用工具的名称、功能描述和参数格式。没有工具定义， Agent 就无法识别和调用任何工具——消融实验（实验 1-1）将验证这一点。工具定义与系统提示词一起构成对话中保持不变的静态前缀（这是基础模式；2026 年以来，生产框架中工具的完整 schema 也可以按需动态加载到上下文末尾而不破坏前缀，详见第二章工具定义一节和第四章）。

用户消息（User Messages）：来自用户的输入。用户消息中还可能包含通过 RAG（检索增强生成，Retrieval-Augmented Generation，详见第三章）动态检索引入的外部知识——覆盖训练数据截止后的信息或私有领域知识。

模型回复（Assistant Messages）：模型之前生成的回复，最多包含三个部分——思考过程（reasoning，即内部思考链，用于保持思维的连贯性和决策的可解释性）、文本内容（content，即对用户的回复）和工具调用请求（tool_calls，即 Agent 采取行动的方式）。在一次具体的回复中，三者不一定同时出现：例如 Agent决定调用工具时通常只有 reasoning + tool_calls，给出最终回答时通常只有 reasoning + content。

工具执行结果（Tool Results）：Agent 框架执行工具后返回的结果。这些结果是 Agent 下一步思考的直接依据，也让它能够从执行结果中学习、避免重复犯错。


### ReAct 循环

Agent 执行任务的核心模式叫做 ReAct （Reasoning + Acting）。虽然名字只体现了思考（Reasoning）和行动（Acting）两个词，但实际循环包含三个环节：模型先思考当前应该做什么，然后调用工具行动，再观察工具返回的结果并继续思考下一步。这个“想 → 做 → 看 → 想 → 做 → 看”的循环不断重复，直到任务完成。

每一次调用 LLM 时，它接收的完整上下文由静态前缀 （系统提示词 + 工具定义）和轨迹 （动态消息历史）两部分组成。这揭示了一个关键事实：**Agent 的上下文= 静态前缀 + 轨迹**。


## Harness 工程：模型之外的竞争力

到这里你已经理解了 Agent 的核心工作原理——LLM 通过 ReAct 循环，在上下文的辅助下使用工具完成任务。前面的实验证明了这套基本机制是有效的，但同时也暴露了明显的脆弱点：模型可能产生幻觉（编造不存在的工具或参数）、选错工具，或在遇到错误时无法自我恢复。一个能跑的 Demo 和一个可靠的产品之间还有巨大的鸿沟，而这些脆弱点正是 Harness 工程要解决的问题。本章前半部分回答了 Agent 是什么，下半部分回答 Agent 如何在生产环境中可靠运行。

前面几节建立了 Agent = LLM + 上下文 + 工具的最小工程公式。从 Harness 工程的视角看，可以把 LLM 抽象为核心组件 Model，把 Agent 边界内负责支撑模型运行及模型与环境交互的代码、配置和服务统称为 Harness。两个视角并非替代关系，而是不同抽象层次上对同一 Agent实现的描述。Harness 的核心是原公式中的“上下文管理 + 工具接口”，再加上三层保障机制：**约束（限定 Agent 能做什么、不能做什么）、验证（检查 Agent 做得对不对）和纠正（做错了怎么补救）**。

用方程展开生产形态下的完整组成：
- Agent = Model + Harness
- Harness = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正
- Agent ↔ Environment

更精确地说， **Harness 不是模型之外的一切，而是 Agent 边界内、模型之外的运行与治理层**


五个功能构成一个闭环：上下文与工具让 Agent “能做事”——理解任务并采取行动；约束预防错误，验证发现偏差，纠正使闭环得以形成，三者共同让 Agent “不做错事”。它们不是独立于上下文和工具之外的东西，而是确保上下文和工具在生产环境中可靠运转的工程实践。缺少任何一个环节，系统都会出现可靠性缺口。而在 Agent 产品的成熟度曲线上，两类功能的重要性是不对称的。


以 Claude Code 为例，它的 Harness 中绝大部分代码都是约束、验证与纠正，而非上下文与工具——工具本身（文件读写、命令执行、搜索）只是一小部分，而围绕这些工具构建的保障机制才是真正的核心。这些机制包括：
- 流程状态管理：追踪 Agent 当前执行到哪一步
- 多层上下文压缩：当信息太多时自动精简
- 权限分类：控制哪些操作需要用户确认
- 熔断器（Circuit Breaker）：当错误连续发生时自动“断电”停止重试——就像家里电路短路时保险丝会自动跳闸，防止整个系统崩溃
- 错误恢复机制：捕获异常、回滚到上一稳定状态、重试或交还给人类


### 从提示工程到 Loop 工程：工程范式的演进

提示工程（Prompt Engineering）是第一波创新——通过优化输入给模型的自然语言指令来提升输出质量。

上下文工程 （Context Engineering）是第二波——人们认识到单纯优化提示词还不够，需要系统性地管理模型能看到的所有信息（系统指令、工具定义、对话历史、外部知识）。

Harness 工程是第三波——它将视野从“模型能看到什么”进一步扩展到“Agent 如何组织模型运行并与环境交互”，涵盖上下文与工具接口、约束机制、验证手段、反馈循环和错误恢复等 Agent 边界内、模型之外的运行与治理机制。


### 构建有效 Agent 的核心原则


保持简单。从最简单的方案开始，只在确实必要时才增加复杂度。直接的 API 调用优于复杂的框架，清晰的代码优于聪明的抽象。因为每多一层抽象都会成为以后调试时新的盲区。

保持透明。明确显示 Agent 的规划步骤、执行日志和决策轨迹——这不只是为了调试方便，也是让用户建立信任的前提。因为黑箱里的错误一旦发生，外部观察者既无法定位也无法纠正。

设计好工具接口（ACI，Agent-Computer Interface）。ACI 强调的是从 Agent 视角设计接口（让 Agent 容易理解和使用），而非传统 API 从程序员视角设计接口。工具的命名和参数要直观，容易误用的地方要从设计上让错误无法发生——比如 SIM 卡的缺角让卡片只能从一个方向插进卡槽，避免了用户插反的错误；微波炉门没关好就绝不加热，避免了用户开门加热的危险行为。设计不好的工具会让再强的模型也频繁出错——因为模型与工具之间唯一的沟通通道就是接口本身，模糊的接口会被模型放大成系统性的错误。

以下三节展开 Harness 工程中三个独立但重要的主题：模型选型、编排模式、护栏与安全性。它们都不属于Harness 五要素本身，但是工程实践中绕不开的决策。



## 思考题

1. ★★ 如果你只能给一个 Agent 系统增加一项能力——更强的模型、更丰富的上下文还是更多的工具——你会选哪个？在什么条件下你的选择会改变？

答：其实就是影响范围依次缩小，我的选择也就反过来了。在效果验证期，工具优先，因为解决具体问题最快；在优化期，上下文优先，因为性价比最高；在极致期，模型优先，因为只有它能突破上限。 这个顺序会根据预算、任务类型和系统稳定性要求动态调整——没有绝对的最优，只有最合适的取舍。


2. ★★★ ReAct 循环中，累计缓存读取量随轮数近似二次方增长。如何降低这种增长？

答：一般会采取滑动窗口和压缩的方式来处理，但是如果任务依赖早期决策（比如多步推理的"链式依赖"），压缩和滑动都可能**截断关键信息**，导致 Agent"失忆"。这里可以采取分层存储，使用滑动窗口处理短期记忆，而相关长期记忆需要 LLM 进行提炼存储重要信息，当然这增加了成本。还有一些任务，比如拨打电话限制三次这种，我们可以将自然语言的回答提炼成结构化的状态信息。比如
```
用户说想要去东京，预算5000元，时间3天，偏好美食和购物
-->
{destination: "东京", budget: 5000, days: 3, preferences: ["美食","购物"]}
```


3. ★★ “模型即 Agent”范式意味着模型在工具调用决策上越来越自主。但本章论证了 Harness 工程的重要性反而在增加。这两个趋势如何共存？Agent 框架未来的核心价值体现在哪些方面？

答：就像汽车一样，一步一步慢慢进化，以后可能会达到全自动驾驶，不怀疑未来模型能力会吃掉 Agent。但就目前来看还很远，比如数据安全如何保证？


4. ★★ 消融实验中“工具结果反馈”的缺失导致 Agent 陷入无限循环。在生产环境中，除了工具结果缺失，还有哪些情况可能导致 Agent 无限循环？你会设计怎样的检测和终止机制？

答：生产环境中，以下三种情况更隐蔽、更常见：

“死循环”式自我纠偏（模型对齐失效）
现象：Agent 发现第一步的思考有问题，于是重新生成 Thought，但新 Thought 又发现第二步有问题…… 它一直在“思考如何思考”，而不是采取 Action。
根因：System Prompt 中强调“必须严谨”或“必须验证”，模型为了追求完美，陷入了无限的内省（自我反思）循环。

环境状态未更新（无效操作）
现象：Agent 反复调用同一个工具（比如 get_weather），但传入的参数完全相同，每次返回的结果也完全相同。
根因：Agent 没有“缓存”意识，或者它认为下一次调用可能结果会变（这其实是模型对“幂等性”缺乏理解）。

上下文“淹没”了指令（Lost in the Middle）
现象：当历史 Observation 越来越长（二次方增长），关于“终止条件”的 System Prompt 被淹没在中间位置。模型“忘记”了自己该在什么条件下输出 Final Answer，只能机械地重复 Action。

常见解决办法：

| 层级           | 检测策略                                         | 触发条件               | 灵敏度                       |
| ------------ | -------------------------------------------- | ------------------ | ------------------------- |
| **L 1：步数闸门** | 计数步数                                         | 步数 > 阈值（如 30 步）    | **最高**（兜底）                |
| **L 2：状态去重** | 计算最近 N 步（如 5 步）的 `Action+Input` 哈希值          | 连续 3 次哈希值完全相同      | **中高**（发现原地踏步）            |
| **L 3：信息增益** | 对比本轮 Observation 与上一轮的**文本差异度**（Jaccard 相似度） | 相似度 > 95%（几乎没有新信息） | **中**（发现信息停滞）             |
| **L 4：语义停滞** | 用嵌入模型计算最近 3 轮 Thought 的余弦相似度                 | 相似度 > 0.95（想法没变）   | **低**（较难发现，但一旦发现就是严重 Bug） |

制终止（抛异常）是最简单的做法，但用户会看到一个冰冷的错误。在生产环境中，我们更关注失败后的降级与恢复：

注入“反思”提示（给Agent一次自救机会）：
当L2或L3探针触发时，先不终止，而是强行向对话上下文中插入一条系统消息：“警告：检测到循环。请分析：1. 工具是否可用？2. 是否遗漏关键信息？3. 如果无法解决，请直接总结现有信息。” 强制模型跳出循环并给出Final Answer。

兜底回复（确保用户体验）：
如果自救失败，步数闸门触发。此时并非直接报错，而是启用降级策略——将截至目前的历史Observation和用户问题，抛给一个非Agent的普通LLM（如GPT-4o-mini），Prompt为：“根据以下碎片化日志，礼貌告知用户系统繁忙，并给出可能的解决建议（如转人工或重新描述问题）。”

异步恢复（高级策略）：
对于一些耗时的任务，终止会话后，可以将当前的完整状态（State）持久化到数据库。当用户再次进入时，提示：“上次任务未完成，是否继续？” 这利用了LangGraph的Checkpointer机制，能实现任务的断点续传。

更进一步：
单纯的硬终止是‘暴力切断’。而在生产环境中，我更倾向于使用 **LangGraph 提供的 `interrupt`（中断）结合持久化检查点（Checkpointer）**。当 L2 去重探针触发时，我并不会立即报错，而是通过 `interrupt` **挂起**该节点的执行，并将当前完整的上下文快照（包括 Thought 轨迹、工具调用状态）持久化到 Redis。此时，我可以外部介入（人工审核或调整 Prompt），然后**从断点处恢复执行**。这种方式比起‘终止并报错’，能极大提升复杂任务的成功率，也是实现人机协同（Human-in-the-Loop）的关键技术。

但这里会有一个误解，就是既然都循环了，那再恢复也没啥意义。其实 LangGraph 的 checkpointer 不仅仅在于恢复执行，而在于提供可回溯的状态快照，这里可以做三件事：
离线根因分析：通过回放进行问题定位
调试：在修改 Prompt 或其他内容后可以节点重放调试
构建回归测试集：最后可以将失败样本收集为测试集

而人工干预只是最后的兜底措施。


5. ★ 本章用感知、行动、策略三个维度分析了五个 Agent 产品。请选择一个你日常使用的 AI 产品，用这三个维度进行分析，并思考它的架构设计是否合理。如果由你来设计这个 AI 产品，有哪些改进空间？

答：
以 ChatGPT 为例

### 1. 感知（Perception）

| 能力                          | 实现方式                        | 评价                         |
| --------------------------- | --------------------------- | -------------------------- |
| **文本输入**                    | 原生支持                        | ✅ 基础能力                     |
| **文件上传**（PDF/Word/Excel/图片） | 多模态解析 + RAG 分块索引            | ✅ 支持，但大文件检索精度有限            |
| **图片理解**                    | GPT-4 o 多模态视觉编码             | ✅ 很强                       |
| **上下文记忆**                   | 全量上下文窗口（1 M tokens）+ 滑动窗口   | ⚠️ 全量保存导致长对话 Token 消耗巨大    |
| **联网搜索**                    | Bing 搜索 API → RAG 检索 → 摘要生成 | ⚠️ 搜索质量依赖 Bing，且有时"忘了"开启搜索 |
| **语音输入**（高级语音模式）            | 端到端语音模型（非 ASR+LLM 拼接）       | ✅ 技术领先，能感知语气/情绪            |

**感知层的设计合理性**：ChatGPT 的感知是"全能型"——什么都能吃，但**没有做感知优先级管理**。例如，用户上传一个 200 页 PDF 问一个问题，系统会把整个文档都分块索引，但其实只需要其中的 3 页。

### 2. 行动（Action）

|能力|实现方式|评价|
|---|---|---|
|**文本生成**|核心能力|✅|
|**代码执行**（Python 沙箱）|内置 Code Interpreter|✅ 能跑代码、做数据分析|
|**DALL-E 绘图**|图像生成工具|✅|
|**文件导出**（生成 PDF/Excel 下载）|工具调用|✅|
|**第三方插件**（已下线）|曾经支持，现在转向 GPTs|❌ 插件生态被大幅削弱|
|**MCP 工具调用**|尚未原生支持（2026 年趋势）|❌ 落后于 Claude 等竞品|

**行动层的设计合理性**：ChatGPT 的行动能力**覆盖了"创作"和"计算"**，但**缺少"执行"**——它不能帮你发邮件、订机票、改系统设置。这是 OpenAI 的战略选择（不做"操作系统级 Agent"），但对用户来说，行动能力是"半残"的。

### 3. 策略（Strategy）——这是最核心的维度

|能力|实现方式|评价|
|---|---|---|
|**模型选型**（何时用 4 o/4 o-mini/o 1）|用户手动选择，非自动路由|❌ 普通用户根本不知道怎么选|
|**工具调用决策**（何时联网/何时用代码）|LLM 自主判断，由 System Prompt 引导|⚠️ 经常判断失误（例如应该联网却没联网）|
|**多轮对话管理**|全量上下文保存|❌ 长对话成本失控|
|**终止条件**|用户手动停止 / 模型自然结束|⚠️ 无主动"终止确认"机制|
|**人机协同**|无|❌ 不支持人工介入审核敏感输出|
|**记忆持久化**|用户手动管理"记忆"（可删除/编辑）|✅ 做得不错，但记忆召回不够智能|

**策略层的设计合理性**：ChatGPT 的策略是**"把决策权推给用户"**——模型选型用户选、是否联网用户开、记忆用户自己管理。这对 OpenAI 来说是**降低风险**的策略（出了事用户自己负责），但对用户体验来说是**转嫁认知负担**。


评价：

|维度|评分（满分 5）|理由|
|---|---|---|
|**感知**|⭐⭐⭐⭐|多模态能力全面，但缺少感知优先级管理|
|**行动**|⭐⭐⭐|能做"创作"和"计算"，但做不了"执行"（发邮件/订票）|
|**策略**|⭐⭐|**最大短板**——把所有决策压力都丢给了用户|

**核心问题**：ChatGPT 的架构是**"被动响应式"**，而不是**"主动决策式"**。它等用户告诉它怎么选，而不是自己判断最优路径。


如果让我重新设计，我会做三件事：（其实就是现在 harness 正在做的）
加一个智能路由层，用小模型自动判断用 4 o 还是 o 1 还是 mini，用户只选"快/准/省"三种模式。
把上下文管理改成三层架构：最近 5 轮全量、早期对话做摘要压缩、更早的按需向量检索，长对话成本能降 60%。
接入 MCP 协议做真实操作，但配上分级确认机制——低风险自动、中风险确认、高风险阻断，既扩展了行动能力，又守住安全底线。


6. ★★ 如果你要设计一个专门处理航班订票的客服系统，你会选择工作流模式还是自主 Agent 模式？有没有可能在同一个系统中混合使用两种模式？

答：
可以把这个设计总结为 **“感知-行动”分离架构**。

- **感知层（自主 Agent）**：负责处理所有 **“不确定性”** 。用户说的话是随意的、不完整的，比如“我想下周去上海，大概三四天，帮我看看机票”。Agent 的强项是理解意图、提取关键信息（如时间、地点）、处理各种闲聊和异常问法。它的价值在于**把模糊的“人话”翻译成结构化的“机器指令”**。
    
- **行动层（确定性工作流）**：负责处理所有 **“确定性”** 。一旦 Agent 把用户的意图翻译成了结构化的参数（如 `{出发地:深圳, 目的地:上海, 日期:下周三}`），系统就立刻**“移交控制权”**给传统的工作流或预订引擎。因为查票、算价、下单这些步骤是**确定的、标准化的**，用工作流来做，**成本最低、最可靠、最易审计**。

其实就是做一个路由进行拆分。


7. ★★★ 护栏部分提到了工具风险评级。如果一个工具在大多数情况下是低风险的，但在特定参数组合下变为高风险（如 delete_file 删除普通文件 vs 删除系统文件），你会如何设计动态风险评估？

答：**静态风险评级完全不够用，必须做动态上下文感知的风险评估。**

**第一层是静态基线**，每个工具注册时人工定一个 1~10 的基础风险分。

**第二层是参数敏感度分析**，这是核心。我会为每个参数定义危险特征检测函数，比如 `file_path` 检测是否指向 `/etc/`、是否包含通配符、是否匹配关键文件白名单。多个危险参数组合时，用**乘法**计算系数，因为风险叠加不是线性的。有些场景可能直接限制工具参数只能指向哪些路径。

**第三层是上下文威胁建模**，综合考虑用户身份、会话历史、操作连续性、外部威胁情报等因素，做±3 分的修正。

最终得分对应五级决策：**自动执行、轻量确认、双重验证、阻断告警、冻结会话**。



8. ★★ 本章的 Agent 产品表格中，所有 Agent 的动作空间都是“开放式”的。一个受限的动作空间（比如只能从预定义选项中选择）在什么场景下反而优于开放式？

答：对于相关安全性要求较高（比如金融、医疗、法务合规）、比较明确的场景，受限的动作空间更好。很多垂类业务都比较合适受限空间。

优势 1：数据飞轮更容易建立
受限动作空间产生的用户行为数据是**标准化的、可枚举的**，可以直接用于训练一个**意图分类器**或**推荐模型**，而不是一堆自由文本需要做大量的后处理清洗。

优势 2：成本大幅下降
每个按钮点击的成本 = 0（纯前端逻辑），而每个开放式 Action 的成本 = 一次 LLM 推理。如果每天有 100 万次操作，两种方案的成本差异是天壤之别。

优势 3：更容易做 A/B 测试
受限空间里的每个选项都是一个变量，你可以轻松测试"按钮颜色、文案、顺序"的变化对用户转化的影响。开放性对话里做 A/B 测试几乎不可能有统计学意义。

优势 4：更容易覆盖边界条件
受限动作空间的行为矩阵是有限的，可以在上线前**穷举测试所有组合**，确保没有遗漏。开放式 Agent 的行为组合是无限的，永远无法完全测试。


9. ★★ 人工干预机制要求 Agent 能“优雅地移交控制”。但在实践中，用户可能不在线、响应很慢、或者给出模糊的指令。此时 Agent 应该怎么办？
答：

**模糊指令"的进阶处理策略**

你提到"模糊指令继续追问"，这是标准做法。但现实中用户会给出**四种不同程度的模糊**，处理方式各不相同：

|模糊程度|示例|Agent 策略|是否追问|
|---|---|---|---|
|**L 1：参数缺失**|"我要订机票"（没说到哪）|主动提问补全|✅ 必须追问|
|**L 2：参数模糊**|"去上海，大概下周三"|检索候选，展示选项让用户选|✅ 温和追问|
|**L 3：授权模糊**|"你帮我定一个吧，靠谱就行"|**自主决策 + 事后确认**|❌ 不追问，直接执行+通知|
|**L 4：前后矛盾**|"我要最便宜的" + "我要头等舱"|指出矛盾，请用户澄清|✅ 追问（指出矛盾点）|

**L3 是最有趣的**——"你看着办"看起来是模糊指令，但实际上用户**已经授权了**。这时候再追问"您具体想要哪个？"反而是糟糕的体验。

**设计原则总结**

| 原则          | 具体含义                          |
| ----------- | ----------------------------- |
| **非阻塞原则**   | Agent不能因为等用户而卡死，必须有超时和降级      |
| **状态持久化原则** | 每次人工干预节点都要保存Checkpoint，支持断点续传 |
| **多通道通知原则** | 不能只在App里等，要Push/短信/邮件多路触达     |
| **可回溯原则**   | 超时/取消/失败都要有完整日志，方便分析和优化       |
| **人性化边界原则** | "你看着办"不是模糊指令，而是用户信任的体现，要善用    |



10. ★★★ 引言指出“好的设计原则应该穿越模型的迭代周期”，但实现这些原则的具体工程手段可能会随模型能力进步而过时。试举一个这样的 Agent 工程手段，并说明理由。
答：

比如一个金融业务处理流程，安全性和准确性要求较高，其办理流程相对固定。如果让模型来编排，可能产生幻觉，所以可以先由相关工具进行编排判断。在模型能力提升了，相关的业务办理工具还是可以使用，只是将编排工作交给模型，这样灵活度更高。

这里和之前说的将确定的事交给工具，将宽泛的问题交给模型判断这个设计原则是一致的，这里其实就需要路由，而路由这个工作并不会因为模型能力提升就变得不重要，相反往往是一个性价比很高的设计。
