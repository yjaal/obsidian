## 功能简介

Sentinel 是阿里巴巴开源的**面向分布式服务架构的流量治理组件**，以“流量”为切入点，从流量控制、熔断降级、系统负载保护等多个维度保障微服务的稳定性。

> 注意：它和 Redis 的 Sentinel（哨兵）是两个完全不同的东西，Redis Sentinel 负责主从切换，Alibaba Sentinel 负责流量防护。

## 🛡️ 核心能力：四道防线

Sentinel 的核心价值是防止“服务雪崩”——即某个下游服务变慢或挂掉后，调用它的上游服务线程被耗尽，故障沿调用链一路向上蔓延，最终拖垮整个系统。为此，它提供了四层防护：

**流量控制（限流）**
在下游服务处理能力有限时，主动拒绝超出阈值的请求。Sentinel 支持 QPS、并发线程数等多种统计维度，并提供快速失败、Warm Up（冷启动预热）、匀速排队等流控效果。

**熔断降级**
当依赖服务不稳定（如响应时间飙升、异常比例过高）时，自动“熔断”对该服务的调用，让请求快速失败，避免调用方线程被长时间阻塞。熔断器会在冷却期后尝试半开恢复。

**系统自适应保护**
从系统整体负载出发，根据 CPU 使用率、入口 QPS、系统 load 等指标动态调整放行流量，让系统在能力范围内处理尽可能多的请求，而不是简单地在某个固定阈值上“一刀切”。

**热点参数限流**
针对特定“热点”参数（如某个高频访问的商品 ID）进行精细化的流量控制，避免个别热点数据拖垮整体服务。

## ⚙️ 工作原理与架构

Sentinel 的核心设计是 **ProcessorSlotChain（处理器槽链）**，采用责任链模式。每个受保护的资源都会创建一条槽链，请求依次经过各个 Slot，每个 Slot 负责一项具体职能：

- **NodeSelectorSlot**：构建资源调用路径树。
- **ClusterBuilderSlot**：汇总资源的统计信息（QPS、RT、线程数等）。
- **StatisticSlot**：实时记录和统计运行时指标。
- **FlowSlot**：根据限流规则判断是否放行。
- **DegradeSlot**：根据熔断规则执行降级。
- **SystemSlot**：根据系统整体负载控制入口流量。

规则可以通过 **Nacos、Apollo、ZooKeeper** 等配置中心动态推送，无需重启服务即可实时生效。

## 📊 与 Hystrix 的关键差异

Sentinel 常被拿来与 Netflix Hystrix 对比。两者的核心思路不同：Hystrix 侧重**隔离**，Sentinel 侧重**流量治理**。Hystrix 已于 2018 年进入维护模式，Sentinel 是其主流替代方案。

| 维度 | Sentinel | Hystrix |
|:---|:---|:---|
| **隔离方式** | 信号量（轻量，无额外线程） | 线程池/信号量 |
| **熔断策略** | 支持 RT、异常比例、异常数 | 主要基于异常比例/数 |
| **流控能力** | 丰富（QPS、线程数、预热、排队） | 有限 |
| **规则配置** | 动态推送，实时生效 | 本地配置，修改需重启 |
| **系统自适应保护** | 支持 | 不支持 |
| **维护状态** | 活跃更新 | 维护模式 |

Sentinel 在国内 Java 微服务生态（尤其是 Spring Cloud Alibaba）中是流量治理的事实标准，适合需要动态流控、熔断降级和系统保护的场景。


## 接入生产

组件本身自带的管理 Dashboard 无法直接接入生产，因为数据都是在内存中。

社区里常见的改造方向主要有两个：

1. **规则持久化**：接入 **Nacos**、Apollo、ZooKeeper 等配置中心，让规则从“内存”变成“外部存储”，这样控制台重启后规则不会丢，也能实现动态推送。
2. **数据持久化**：将监控数据写入 MySQL、InfluxDB 等数据库，方便做历史查询和告警。


## 与一般系统中 Gateway 的功能区别

Sentinel 和系统本身的 Gateway 在“限流”这件事上确实有功能重合，但它们的**定位、粒度和职责层次完全不同**。简单说，Gateway 做的是“进门时的粗筛”，Sentinel 做的是“房间里的精细管控”。

### 📊 核心差异：入口层 vs 应用层

两者是**协作关系，而非替代关系**，主要区别在于作用范围和管控粒度：

*   **网关层（Gateway）**：位于系统**最外层**，面向所有**外部入站流量**。它的限流通常是**路由级**的粗粒度管控，比如“`/api/order` 这个路由整体 QPS 不能超过 5000”。它像大楼的**门禁**，主要挡住超大流量冲击，不关心进来的是谁、具体要干什么。
*   **应用层（Sentinel）**：深入**微服务内部**，面向**服务间调用（内部流转）** 或**单接口/方法**。它的限流是**资源级**的，粒度极细。比如“用户 ID 为 123 的用户，每秒最多调 10 次 `/pay` 接口”，或者“下单流程里调用库存服务的并发线程数不能超过 50”。它像大楼内部的**房间管理员**，管的是具体业务逻辑的负载，甚至能针对某个热点参数（如某个被疯狂刷的商会 ID）单独限流。

### 🛡️ 为什么需要两者配合？

一个完整的防护体系通常采用 **“多层联合限流”** 架构，各层承担不同职责：

1.  **第一道：Gateway（粗筛）**：在流量进入应用前，按路由或 IP 挡住超出系统总容量的请求。**优势**是不消耗后端应用线程，廉价且高效。
2.  **第二道：Sentinel（精控/兜底）**：Gateway 放行的请求进入微服务后，Sentinel 开始工作。它做三件 Gateway 做不了的事：
    *   **用户级管控**：防止单个用户通过网关后，在服务内部疯狂刷接口（脚本速度优势）。
    *   **熔断降级**：Gateway 限流解决“量太大”，Sentinel 解决“下游变慢”。当下游服务响应超时，Sentinel 能在**调用方**直接快速失败，避免线程池被拖死，引发雪崩。
    *   **热点防护**：Gateway 全局限流拦不住“总 QPS 不高，但某个特定参数（如某热门商品 ID）被集中猛刷”的情况，Sentinel 的热点参数规则可以精准打击。

### 💡 一个典型的故障场景

有个真实的案例很能说明问题：某系统网关设了 1500 QPS 的限流，但活动期间实际流量到了 3000 TPS，**限流却失效了**（因为规则同步延迟），请求直接穿透网关打到了后端服务。如果后端服务里埋了 Sentinel 的熔断降级，当风险校验服务开始超时，Sentinel 就能及时切断调用，保护住整个调用链，而不是让故障一路蔓延。

所以，**Gateway 管的是“谁能进来，总共进来多少”，Sentinel 管的是“进来之后，每个业务怎么安全地运行”**。两者叠加，才能构成一个从外到内、由粗到细的完整防护网。
