
## 需求

内部系统：一般 10k 级 的用户量
外部系统：超过 100 万级

假设是一个内部系统。

那我们需要考虑设计什么样的调度系统？

先做一个基础的功能。

有哪些任务类型？常驻 service 和临时 task


## 分析

应该有哪些功能？
1、提交任务（常驻和临时）
2、执行状态或结果可观测
3、高级功能：设置定时任务；任务依赖

非功能型需求：
1、延迟型
- 提交任务后 10s 执行
- 60s 后同步状态
2、可扩展
3、可靠性-失败后重新拉起


Model
```
config-可执行的二进制问津
元数据
```

```sql
job id
config url
input path
output path
create_time
status: ready -> wating -> running -> S/F(retry -> waiting或者结束)
retry_times  3
```


一般会有 client，client 连接 gateway。然后有两个功能，一个提交，一个 dashboard 查看状态。同时可执行的文件需要单独保存，再加一个任务的保存数据库。

然后需要一个 queue 和一个 worker pool，用户执行 task。

如果 10 k 用户，每天提交 100 个 task。QPS 约在 10 比较低。峰值算 500，也不是很高。

数据库可以做主备。用 nosql 也可以。


那这个队列 queue 就要看看是否做持久化，扩容会比较麻烦点。

这里还有个点可以考虑，就是 config 和 queue 是不是一定要分开存储，理由并不是那么充分。


那这里 database 和 queue 能不能用一个呢？比如直接用 kafka？也就是流表一体，但是维护成本也要考虑。而直接将 database 也可以作为 queue，也是可行的。

这里 worker pool 可以采取的方式也就是 pull、push 或者混合模式。

同时在 client 上层还可以做一个 cron service。

还可以做一些系统调度的算法来压缩资源等，比如区分 io 密集型和 cpu 密集型任务，常驻任务还是临时任务。还有任务的重要级别分为可抢断或者不可抢断等等。
