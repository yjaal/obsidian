## 扩展数据库

### 需求

承载多少 QPS

一亿日活用户，每天 10 次手机，发一两次帖子，于是 QPS 就是读取
```
1亿*10/24h 大约为 10K
```

峰值算 5 倍为 50K，一般 MySQL 支撑不住，读取一般在 1K～5K 左右。


### 分析

一般有两个方案复制和分片

**复制**
一台 master，另外多台 slave。也就是读写分离。但是这里 master 还是一个单点机器。

假设每天发 2 次帖子，平均就是 2K 的写入 QPS，峰值就是 10K 的 QPS，那写入会支撑不住。MySQL 写入不会超过 1K 的写入。

**分片**
那么帖子中有两个字段可以进行分片（比如取模分片），帖子本身的 id 和用户 id。如果选择用户 id 进行分片，那么可能存在有些网红，那么就会导致大量负载涌入同一个数据库节点；同时如果有很多网红刚好分片都分到了同一个分片，那么就更会加重这种情况。这里一般推荐使用 post_id 进行分片。

但是使用 post_id 进行分片比较随机，这是优点；但是坏处就是可能为了查某个人的帖子就需要查询很多个分片，然后需要在应用层进行聚合，可能导致查询出现问题，比如最新的 10 篇帖子。而且分片数量可能随时发生变化，那怎样去移除和添加分片呢？


## 优化延迟

### 引入缓存

缓存最近三天的帖子，一亿用户，每个人每天发两次帖子，一般限制帖子的长度是 140 个字符* 2 bytes + 12 bytes 其他内容，算 300 bytes，一般比这个大一些。那总共就是 180 G。

假设 20%的帖子占用 80%的流量，算下来就是 36G 缓存空间。够用


那能不能更快一些呢？那可以增加一个时间线 cache，这个在用户登陆后就可以看到最近的帖子。

在用户发帖时将其发送到其好友的时间线上去，此时需要进行一个异步处理。也就是需要构建一个 MessageQueue，使用一个 Worker Pool 去处理，当然这个也不能保证别人就立即能看到帖子，因为有延迟，但是影响不大。那 Worker Pool 的数量可以根据 MessageQueue 中的数量动态调整。这样你发了帖子之后就可以立马写入到好友的时间线缓存上。计算下这个时间线 cache 占用空间在

```
1亿*8B（post_id,user_id）*100条，大约为80G空间
```

下面要计算下 QPS：

假设每个人有 100 个好友，按照之间算的写入就是 `100*2K=200K QPS`，这个峰值就优点不太好算了。因为比如川普可能有 一亿好友，马斯克有 2 亿好友，对于这些人来说一次写入就变成分很多倍。

那这里就分为 push 和 pull 两种模式，像上面这种 push 的方式，就是一次写入就直接写入到时间线 cache，对于好友数很多的人 push 就会被放大很多倍；另一个是并不是所有用户都是活跃用户，就没必要建 cache 了。对于 pull 模型来说就是登陆之后进行拉取，push 就是在帖子写入时就写入 cache。

于是 pull 模式下对于不活跃用户是不消耗资源的，缺点就是是在时间线 cache 是在时候生成的，延迟较高。由于在登陆后才做一些事情，那么就没办法在用户登陆的时候就及时给用户进行一些推送。

现在就要看能不能将两种方案进行合并？

是不是可以给用户建立一个活跃值，根据各种指标，如是否每日登陆、发帖数等等计算其活跃度，根据活跃度决定是使用 pull 模式还是使用 push 模式。



## 补充

Message Queue 怎么选？

需求分析→列举可行方案-→比较方案之间平衡。

比如使用场景是任务队列还是事件流？高吞吐优先还是低延迟优先？有无顺序要求/持久化要求？有些现有数据系统的特性要记住：

Kafka高吞吐、低延迟、consumer group、可持久化；
SQS：托管、最省心、可用性高、DLQ/重试/FIFO; 
RabbitMQ:路由（exchange）很强、低延迟、ack/prefetch
