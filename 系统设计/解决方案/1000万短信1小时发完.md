## 为什么不推荐使用 Executors

在大厂规范里，严禁使用 `Executors.newFixedThreadPool` 或 `newCachedThreadPool`。

- **OOM 隐患：** 默认的无界队列能塞 231−12^{31}-1231−1 个任务。在 1000 万数据的冲击下，还没等到线程处理，你的 JVM 堆内存就先爆了。
- **资源耗尽：** `CachedThreadPool` 允许创建的线程数也是无限大，瞬间的高并发能直接把 CPU 100% 跑满。

**Fox 的结论：** 生产环境必须手动创建 `ThreadPoolExecutor`，且必须配合**有界队列**。


## 核心设计

一般使用动态线程池：
1. **参数动态化：** 核心参数（CoreSize、MaxSize、QueueSize）不要写死在代码里，接入配置中心（如 Apollo、Nacos）。
2. **监控预警：** 监控队列剩余容量、线程池活跃度。当队列超过 80% 满时，自动触发告警或动态扩容。

**Fox 提示：** 业内著名的开源项目 `Hippo4J` 或 `DynamicTp` 就是干这个的

`Hippo4J` 动态调整线程池的核心机制是：**用配置中心（如 Nacos）作为参数存储和推送通道，客户端监听到变更后，通过反射直接修改运行中 `ThreadPoolExecutor` 的私有字段**。

### 🔄 整体链路

**1. 配置存储与推送**
`Hippo4J` 将线程池参数（核心数、最大数、队列容量等）存在配置中心。当参数在控制台被修改，配置中心通过**长轮询或推送机制**通知所有客户端实例。

**2. 客户端监听与拉取**
引入 `hippo4j-spring-boot-starter` 的应用启动时，会向 Server 端注册实例，并监听对应线程池 ID 的配置。配置变更时，客户端实时感知。

**3. 核心修改动作：反射赋值**
这是最关键的一步。JDK 的 `ThreadPoolExecutor` 没有提供修改参数的 setter 方法，`Hippo4J` 通过**反射**直接对私有字段赋值来实现动态修改。它会修改：
*   `corePoolSize`（核心线程数）
*   `maximumPoolSize`（最大线程数）
*   `keepAliveTime`（空闲存活时间）
*   `workQueue`（阻塞队列，如果容量变化需要替换队列）
*   `RejectedExecutionHandler`（拒绝策略）

### ⚙️ 不同参数的处理细节

并非所有参数都能“平滑”修改，有些需要特殊处理：
*   **核心/最大线程数**：直接反射修改字段值。如果调大 `corePoolSize`，已有空闲线程会自然补充；如果调小，多余的线程会在空闲后被回收。
*   **队列容量**：JDK 的 `ArrayBlockingQueue` 等队列容量是 `final` 的，无法直接改。`Hippo4J` 的策略通常是**用新容量的队列替换旧队列**，并把旧队列中已堆积的任务迁移到新队列，尽量保证任务不丢失。
*   **拒绝策略**：直接替换 `RejectedExecutionHandler` 字段。

### 📊 核心架构

`Hippo4J` 的架构分为 Server 端和 Client 端：
*   **Server 端**：提供控制台（Console），负责权限、监控、配置持久化。配置变更从这里发起。
*   **Client 端**：你的 Spring Boot 应用，通过 Starter 包与 Server 交互。它负责上报运行时数据，并**执行最终的反射修改**。

### 拒绝策略选择

当 1000 万数据涌入，线程池满了，拒绝策略（RejectedExecutionHandler）选哪个？
- **AbortPolicy（默认）：** 直接抛异常，千万别选，数据直接丢了。
- **CallerRunsPolicy（推荐）：** 让提交任务的线程（比如主线程）自己去执行。 这其实是一种**“天然的背压（Backpressure）”**。主线程去发短信了，它就没空再去数据库捞新任务，从而减缓了任务产生速度，给线程池喘息的机会。

很多同学应该还记得我写过：`CallerRunsPolicy`（回退给调用者执行）是个坑，因为它会阻塞主线程。**但是！在千万级推送这种“离线批量场景”下，这个“坑”反而成了神技。**

- **在线 Web 场景（避坑）：** 如果是处理用户请求，绝对不能用它，否则 Tomcat 线程被占满，整个网站直接卡死。
- **离线批量场景（神器）：** 我们从 DB 里捞千万级数据往线程池塞。如果池子满了，触发 `CallerRunsPolicy`，让“捞数据的线程”自己去发短信。
- **高阶奥义：天然背压（Backpressure）。** 当“生产者”被迫去干“消费者”的活儿时，它就没空去 DB 捞新数据了。这会自动减缓任务产生的速度，给线程池喘息的时间，彻底规避 OOM 风险。

  
## 应对服务宕机

任务在内存队列里，机器宕机了，100 万条短信没发出去，怎么补救？

**满分回答：**
1. **本地持久化：** 在任务入队前，先在数据库/Redis 记录一个“发送中”的状态。
2. **Ack 机制：** 线程处理完后，回调更新状态为“已完成”。
3. **离线补偿：** 启动一个定时任务（T+N），专门扫描那些处于“发送中”超过 10 分钟的任务，重新投递。
