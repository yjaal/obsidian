## MySQL 索引底层结构

MySQL 索引的底层实现取决于**存储引擎**，最常见的是 InnoDB（默认引擎）。

### InnoDB：B+ 树

InnoDB 的索引底层是 **B+ 树**，不是 B 树，也不是二叉树/红黑树。原因：

| 对比结构 | 问题 |
|---------|------|
| 二叉树/红黑树 | 树太高，磁盘 IO 次数多 |
| B 树 | 非叶子节点也存数据，单节点能放的 key 少，树更高 |
| Hash | 不支持范围查询、排序 |
| **B+ 树** | 非叶子只存索引，叶子存全部数据且用链表相连 |

**B+ 树的关键特性：**
- 非叶子节点只存 key（不存 data），所以一个节点能容纳更多 key → 树更矮（通常 3~4 层就能存千万级数据）
- 所有数据都在叶子节点，且叶子节点之间用**双向链表**连接 → 天然支持范围查询和排序
- 查询性能稳定，每次都要走到叶子节点

**聚簇索引 vs 二级索引：**
- **聚簇索引（主键索引）**：叶子节点直接存放整行数据。所以按主键查最快。
- **二级索引（普通索引）**：叶子节点存放的是「索引列的值 + 主键值」。如果查询的列不在索引里，需要拿主键回聚簇索引再查一次，这叫**回表**。

> 补充：MyISAM 引擎的索引也是 B+ 树，但叶子节点存的是**数据的物理地址**，而不是数据本身（非聚簇）。

## 索引失效的常见场景

以下场景主要针对 InnoDB 的 B+ 树索引：

### 1. 违反最左前缀原则
联合索引 `(a, b, c)`：
- `WHERE b = 1` ❌ 跳过 a
- `WHERE a = 1 AND c = 2` ⚠️ 只用到 a，c 用不上（a 相等时 b 无序）

### 2. 在索引列上做运算或函数
```sql
WHERE id + 1 = 10          -- ❌
WHERE YEAR(create_time) = 2024  -- ❌
WHERE name = 'abc'          -- ✅
```

### 3. 隐式类型转换
```sql
-- phone 是 varchar 类型
WHERE phone = 13800000000   -- ❌ 数字转字符串，索引失效
WHERE phone = '13800000000' -- ✅
```

### 4. 以 % 开头的 LIKE
```sql
WHERE name LIKE '%abc'   -- ❌
WHERE name LIKE 'abc%'   -- ✅
```

### 5. 使用 OR 且两侧不全是索引列
```sql
WHERE a = 1 OR b = 2   -- 若 b 无索引，整体失效
```

### 6. 使用 NOT、!=、<> 
通常导致全表扫描（优化器判断走索引不如全表快时）。

### 7. IS NULL / IS NOT NULL
取决于数据分布，NULL 值过多时可能失效。

### 8. 范围条件后的列失效
联合索引 `(a, b)`：`WHERE a > 1 AND b = 2`，a 用范围后 b 用不上索引。

### 9. 优化器认为全表扫描更快
当查询返回的数据量占比很大（一般超过 20%~30%）时，优化器可能主动放弃索引。

## 如何验证

用 `EXPLAIN` 看执行计划：
- `type`：`ALL`（全表）最差，`ref` / `range` / `const` 较好
- `key`：实际用到的索引，为 `NULL` 说明没走索引
- `rows`：预估扫描行数

```sql
EXPLAIN SELECT * FROM user WHERE name = 'abc';
```
