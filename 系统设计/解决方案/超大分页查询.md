## 为什么超大分页查询慢

MySQL 的分页是 **“扫描+丢弃”** 的过程。比如：

```sql
select * from orders limit 100000, 10
```


MySQL 会先扫描 **1000010 条数据**，丢掉前 100 万，再返回 10 条。换句话说，页码越靠后，浪费的扫描越多，性能呈指数级下降。这就好比你去排队取快递，快递员一件件往后翻，找到第 100 万个时，你早就下班了。

所以，问题的关键是：**如何避免无意义的扫描？**

## 利用索引 + 覆盖条件

最经典的优化就是：不要用 offset，而是利用 **索引定位起点**。

比如订单表有主键 id，我们可以改成：

```sql
select * from orders 
where id > 100000
limit 10;
```

这样 MySQL 直接跳过前面数据，定位到 id 较大的部分，不需要做大量丢弃。

这就像快递员直接从第 100 万个快递开始翻，而不是从第一个开始数。不过注意，这个方案要求分页是 **基于主键顺序的**。如果你要按创建时间排序，那就得在 created_at 上建索引。

但是实际情况一般没这么简单


## 延迟关联

还有一个套路：**先用索引字段做子查询，获取主键，再回表查询其他字段。**

```sql
select o.* 
from orders o
join (
	select id from orders
	where created_at >= '2026-07-01'
	order by crated_at
	limit 100000, 10
) t on o.id = t.id;
```


## 业务层面优化

一般管理台都不会让查这么久的数据的，如果一定要查，那么可能让走大数据推送的方式


MySQL8 版本后也支持窗口函数了，可以进行优化
