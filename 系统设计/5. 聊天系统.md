
## 需求

Client-Server

一对一：
- 在线消息传递
- 离线消息

群聊：（人数限制，如小于 200）
用户状态


非功能性需求：
- 可扩展（10 亿用户）
- 低延迟（小于 500 ms）
- 高一致性
- 健壮性


## 分析


1、polling 开销比较大
2、long polling 开销也会较大
3、websocket 主动推送，延迟更低。需要支持额外的协议，兼容性会差一些
4、网络可能不稳定，QUIC 谷歌方案，可以在不同网路区间切换，协议比较新



那这里多台 client 以及多台 server，一个客户发送消息，就需要知道发送到哪里去，这里就需要一个登录 session管理系统，专门进行管理，用户登陆后需要心跳维持，这里就可以做客户在线状态管理，可以推送给好友。

这个 session 管理系统就需要存储一些基本信息,
```
user_id, last_heartbeat:timestamp, chat_server...
```

假设 10 亿用户有 20%日活用户，其中峰值在线 25%，也就是 500 万，如果每条消息 100 byte 也就是 5 GB。量不大，就可以将在线状态推送给好友。

当用户 A 给用户 B 发送消息时，并不知道 clientB 是挂在哪个 server 上，这里第一个方案就是通过 session 管理台查找，将 clientA 和 clientB 挂在同一个 server 上。聊天延时最小。这里的问题就是如果多个单聊会导致非常多的 server 切换，也有业务上的抖动。另外一个问题就是热点机器，某个 server 会承载很多的请求。如果实时性要求不高，或者量不大也是可以的。一般游戏服务器就这么干

第二种就是不进行切换，而使用服务器进行消息转发，此时消息先进行存储，然后转发。这里可扩展性就非常高。缺点就是转发增加了耗时，一致性要求比较高。同时可能两边同时在发消息，不同 server 的时钟可能不同步，要考虑到消息的顺序问题。复杂度会比较高。


那还有另外的就是消息总线 service，有消息先存储到这个 service 中，相关 server 需要进行订阅。持久化和消息排队就比较可靠了。那这个中心化的 service 可能就会成为瓶颈，此时就需要做一些 sharding 来拆分业务量。

假设 10 亿用户，5s 一条消息，峰值时 500 万，也即是 100 万/s 的消息（msg_id, from, to, content, timestamp 约小于 0.5 Kb）也就是每秒 5 GB 的流量。量不是很大。

假设有 20% 的同 server 概率。就可以将 20%的用户使用方案一，80%使用消息总线方式处理。这里一般就将附近的或者好友分在同一个 server 上。如果技术实力足够可以让单机去支撑。否则就可以选择第三种方案，走转发了。

离线消息

客户不在线，上线后就需要将消息拉取回来。需要有一个离线消息的存储。可以简单做，就在推送消息时如果用户不在线就先进行存储，比如使用一个 log_file，或者可以考虑 nosql 等等。
